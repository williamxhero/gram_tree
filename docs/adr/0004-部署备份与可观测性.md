# 0004 部署、备份与可观测性

- 状态：已采纳（2026-09-27，SPEC-013.1 #15）

## 部署

- 阶段一一台服务器，Docker Compose 跑 API、PostgreSQL（`pgvector/pgvector:pg16`）、Redis、任务进程（worker + beat），前面用 Caddy 自动申请 HTTPS 证书。不用 Kubernetes，不拆微服务。
- 服务器先放在无需 ICP 备案的近邻地区；正式面向国内公众前迁回境内（SPEC-011）。云服务商不在这里定。
- API 容器启动时先 `alembic upgrade head`。
- 镜像里用 pip 装 uv（不从 ghcr.io 拉），因为部分网络环境访问不了 ghcr。
- 步骤：`server/deploy/README.md`。

## 备份

- Celery beat 每天 UTC 19:00（北京时间 3 点）跑 `backup_database`：`pg_dump -Fc` 写本机卷，再 `rclone copy` 到服务器之外（`GRAMTREE_BACKUP_REMOTE`）。
- 保留天数是配置项 `ops.backup_retention_days`，本机和异地都按它清理。
- 恢复只恢复到新库，不碰正在用的库；恢复演练（写入 → 备份 → 恢复 → 健康检查 + 读数据）每次提交都由 `server/tests/test_backup_restore.py` 自动跑。

## 可观测性

- 服务端 JSON 日志带请求编号（0002）。
- 接口耗时和状态码按分钟分桶记在 Redis（多个 API 进程共享；Redis 挂了只丢指标）。任务进程每分钟检查一次窗口内的 5xx 比例和耗时 p95，超过阈值就告警；同一窗口只发一次。
- 阈值、窗口、最少请求数、接收方式（none / webhook / email）和接收地址都是配置项 `ops.alert_*`；邮件的 SMTP 服务器是环境变量。
- App 崩溃上报见 0001；同意隐私政策前不初始化，上报前去掉菜谱、口味、健康信息。
- 产品埋点和经验层事件不在这里（SPEC-010.1）。
