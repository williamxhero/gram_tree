# 0003 测试分层，以及网页版只作为测试目标

- 状态：已采纳（2026-09-27，SPEC-013.1 #15）
- 背景：用户要求测试尽量用安卓，但只在用到手机能力的地方用；网页版做全面的功能测试；iOS 和真机由用户自己测。实测云端开发容器没有 KVM，跑不了安卓模拟器，`dl.google.com` 也被网络策略拦住。

## 决定

原则：只测外部行为。服务端只通过对外接口（HTTP、命令行）测；App 只看页面显示和操作结果。

| 层 | 内容 | 在哪跑 | 样板 |
|---|---|---|---|
| 1 服务端接口测试 | 连真 PostgreSQL（含 pgvector）和 Redis；整轮开始时重建测试库、跑完全部迁移；每个测试后清空业务表；AI 调用用录制回答（SPEC-003.1 加） | 云端线程 + CI `server` | `server/tests/conftest.py` |
| 2 页面测试 | 用生成的接口模型构造假数据，覆盖浅色、深色、大字号 | 云端线程 + CI `app`（VM 和 `--platform chrome` 各跑一遍） | `app/test/helpers.dart` |
| 3 网页版端到端 | `integration_test` 编译成网页，在无界面 Chromium 里跑完整流程 | 云端线程 + CI `web-e2e` | `tool/web_test.sh`、`app/integration_test/` |
| 4 安卓模拟器端到端 | 只覆盖网页测不到的手机能力（锁屏计时和通知、分享进 App、相机、离线本地库、后台同步） | 只在 CI `android-e2e`（GitHub 的 Linux 机器有 KVM） | 同一份 `integration_test` |
| 5 iOS 模拟器 | 按需 | CI `ios-e2e`，手动触发（workflow_dispatch） | 同上 |
| 6 真机 | 用户自己安排 | 用户手机 | 每个 PR 正文列“需要真机测试的点” |

### 客户端必须能编译成网页版

- 手机专有能力放在接口后面（`app/lib/platform/device_capabilities.dart`），手机端用真实实现，网页端用替身，页面代码只依赖接口。新增手机能力照这个模式加。
- 网页版不对外发布，只是测试目标。
- CI 里 `flutter build web` 编译不过就失败。

### 网页端到端的坑

- `flutter drive` 必须用 `--profile`：debug 模式下结果回不来，会卡到超时。
- 加 `--no-web-resources-cdn`，不从 Google CDN 拉渲染引擎。
- 云端以 root 运行，Chromium 要加 `--no-sandbox`；chromedriver 主版本要和 Chromium 一致。会话启动钩子会在 `/opt/gramtree-tools/bin` 放好包装脚本 `google-chrome` 和同版本 `chromedriver`。
- 云端没有网络字体，截图里中文会是方框；这不影响按文字查找控件的测试。

### 端到端里"断网""杀进程"这类没法真正模拟的操作系统行为（SPEC-010.1 票 7）

`integration_test` 跑在 App 进程内部，拿不到操作系统权限去真的切飞行模式或杀掉自己
的进程重启（这需要 adb/flutter_driver 层面的操作，不是单个测试用例内能做的事）。
`app/integration_test/event_offline_replay_test.dart`（安卓模拟器专属，网页版用
`kIsWeb` 跳过）踩过这条坑，定下两个等价替代，后面 SPEC-013.3、SPEC-004.2 等涉及
离线的用例可以照抄：

- **断网** → "网络层强制失败"：`lib/api/api_client.dart` 加了一个
  `offlineSimulationProvider`（`NotifierProvider<OfflineSimulation, bool>`，默认
  `false`，只有测试代码会把它翻成 `true`），拦截链最外层命中就直接把请求拒绝成
  `DioException.connectionError`，对上层（队列、上传器的重试逻辑）来说和真的断网
  没有区别。它跟已有的 `fakeServerProvider`（假服务端，不走网络层）不是一回事——
  这里连的还是真的服务端，只是本机不让请求发出去。生产代码永远不会把它设成 true。
- **"杀进程"** → "整个 Riverpod 容器重建，磁盘上的数据不变"：`pumpWidget(SizedBox())`
  之后重新调用 `app.main()`，跟 `app_test.dart`"重新打开 App"那段、
  `event_queue_persistence_check_mobile.dart`"新开一个数据库连接"是同一个思路——
  容器（含上面的 `offlineSimulationProvider`）从头重建，等价于"网络恢复"；drift
  落盘的事件队列和安全存储里的登录状态是磁盘文件，不受容器重建影响。这不是操作
  系统层面真的杀进程重启，只是效果等价的替代，用到这个手法的地方要在注释里如实
  写清楚，不能写成"验证了杀进程"。
- **怎么产生测试要用的真实事件**：这类测试要触发的功能（记一条事件）往往还没有
  业务入口接进去。不要为了测试专门在正式业务里加一个用户能看到的按钮，改用
  Riverpod 公开的 `ProviderScope.containerOf(tester.element(find.byType(...)),
  listen: false)` 直接从 App 正在跑的那棵树里拿到真实容器，再 `container.read(...)`
  调用对应的 provider——走的还是生产代码的完整链路，只是省了 UI 操作。
- **服务端确认"收到"用的测试专用检查接口**：跟 `accounts/dev.py` 的
  `/v1/dev/latest-email-code` 一个模式，新增 `server/gramtree/events/dev.py` 的
  `GET /v1/dev/events/count`（按 `event_type` + 可选 `device_id`/`version` 查当前
  登录用户的事件条数），只在 `dev`/`test` 环境挂载、`include_in_schema=False`，
  只回一个数字，不是对外的事件明细接口。
