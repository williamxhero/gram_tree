# 0005 界面描述协议：共享 JSON Schema 和测试样例放在哪、用什么校验

- 状态：已采纳（2026-09-28，SPEC-009.1 #18 #77）；2026-09-28 按实测结果把 App 端的加载方式从“运行时用 rootBundle 读”改成“编译期内嵌成 Dart 常量”（见文末“App 端踩坑记录”），决定本身（JSON Schema 是唯一来源、两端各校验一次、共用测试样例）没有变。
- 背景：#18 要求页面描述协议和每个组件的数据格式“用 JSON Schema 定义，作为仓库里的唯一来源；服务端输出前、App 渲染前各校验一次”，并且“两端测试共用同一组描述样例”。仓库里此前没有任何跨语言共享契约文件的先例（服务端 Pydantic 模型和 App 生成的 `gramtree_api` 客户端类型各自独立，都是从 `api/openapi.json` 单向派生，不是共享同一份手写 Schema）。

## 决定

### 位置

契约文件放在 `app/assets/contracts/ui_protocol/`，结构：

```
app/assets/contracts/ui_protocol/
  schema/1.0/page_description.schema.json      # 协议信封
  schema/1.0/components/<type>.schema.json      # 每个组件类型的 data 格式
  samples/valid/*.json                          # 合法样例
  samples/invalid/*.json                        # 不合法样例（#79 起补全）
```

它是服务端和 App 唯一共用的来源，两端都只读不改。这些文件**不是** Flutter 运行时会加载的 asset（`app/pubspec.yaml` 没有把这个目录登记进 `flutter.assets`）——App 端通过 `tool/gen_ui_protocol_schemas.sh` 生成的编译期常量读取，原因见文末踩坑记录。放在 `app/assets/` 下面只是沿用“App 相关的静态文件放这里”的目录习惯，服务端从仓库根目录往上找这个路径，读取不受影响。

新增协议大版本时新建 `schema/<major>.0/` 目录，不改旧目录；同一大版本内的小版本只做向后兼容的字段增加，不新建目录。

### 服务端怎么读

`server/gramtree/ui_protocol/schema_validation.py` 用 `Path(__file__).resolve().parents[3] / "app" / "assets" / "contracts" / "ui_protocol"` 定位到这个目录（`ui_protocol` → `gramtree` → `server` → 仓库根，再拼上 `app/assets/contracts/ui_protocol`），用 `jsonschema`（新增到 `server/pyproject.toml` 的依赖）加载并校验。组合接口在返回页面描述前，把 Pydantic 模型 `model_dump(mode="json")` 的结果按这份 Schema 校验一次；校验不过按 #79 的规则整页改用标准布局（#77 阶段只覆盖“默认组合本身必须合法”，校验不过是服务端 bug，返回 500）。

服务端另外用 Pydantic（`server/gramtree/ui_protocol/protocol.py`）定义同构的类型，供 FastAPI 生成 OpenAPI/Dart 类型使用——两份定义都对应同一份 JSON Schema，JSON Schema 校验是运行时的最终把关，Pydantic 类型校验是开发时的类型提示；两者出现分歧时以 JSON Schema 校验失败为准，说明 Pydantic 模型需要跟着改。

服务端测试（`server/tests/test_ui_protocol.py`）用 `gramtree.ui_protocol.schema_validation.load_sample()` 直接读 `samples/` 下的文件。

### App 怎么读

`tool/gen_ui_protocol_schemas.sh` 把 `schema/` 和 `samples/` 下所有文件的内容原样内嵌成 `app/lib/ui_protocol/embedded_assets.g.dart` 里的两个编译期常量（`Map<String, String>`，key 是和 `protocol_paths.dart` 算出来的 asset 路径一致的字符串）：

- `embeddedUiProtocolSchemas`：`ProtocolSchemas`（`app/lib/ui_protocol/protocol_schemas.dart`）渲染组合结果前，用 `json_schema`（新增到 `app/pubspec.yaml` 的依赖，纯 Dart、支持 web）在内存里解析、校验，运行时不读任何文件。
- `embeddedUiProtocolSamples`：只给 App 测试用，读法见 `app/test/protocol_schemas_test.dart`。

Schema/样例文件本身仍然是唯一来源；改了内容就重跑这个脚本，把生成结果和源文件一起提交，不要手改生成的 `.g.dart`。新增组件类型、新的大版本、新的样例都只加文件，两边不用各写一份。

### 为什么不直接用 Pydantic/生成的 Dart 类型做全部校验

Pydantic 模型能保证服务端“不会拼错字段”，生成的 Dart 类型能保证 App 反序列化不出错，但两者都不能验证“旧版本 App 收到不认识的新组件类型时该怎么办”这类协议演进语义（这正是 #79 的核心）。显式的 JSON Schema + 两端各自的校验步骤，才能让“协议校验”这件事本身被测试覆盖，而不只是被类型系统隐式覆盖。

## App 端踩坑记录（2026-09-28）

最初的方案是 App 端在运行时用 `rootBundle.loadString()` 读取契约文件（Schema 给 `ProtocolSchemas` 用，样例给测试用）。这条路径会在**同一个测试文件里第二次读取时卡住或超时**，分两种独立的表现：

1. **Schema，在 `flutter test`（VM）下**：`ProtocolSchemas` 在一个被 Riverpod `FutureProvider.family` 持有、由 `ConsumerWidget` watch 的异步函数里调用 `rootBundle.loadString()`（协议信封一次、每个组件的 data 一次）。文件里第一个 `testWidgets` 正常返回，第二个 `testWidgets`（哪怕内容和第一个完全一样）里这一行 `await` **永远不完成**：不报错、不超时，`pumpAndSettle()` 正常返回，页面停在 `AsyncLoading` 状态——看起来和“组合结果不合法退回标准布局”一模一样（因为两者的文案故意做成一样的），很容易被当成正常的兜底路径而不是 bug。
   排查过程：逐行加打印确认卡住的精确位置就是 `await rootBundle.loadString(assetPath)` 这一行本身。同一个调用直接写在测试体里（不经过 provider）反复调用两次没问题；放进一个不启动完整 App、只搭最小 `ProviderScope` + 单个 widget 的 `FutureProvider` 里也没问题；只有“完整 App 的 Provider 树（`pumpApp`/`GramTreeApp`，路由、认证、同意页等一整套）+ 被 provider 持有的异步函数里第二次调用 `rootBundle.loadString`”这个组合会复现。具体到 Flutter 测试框架/`rootBundle` 内部哪一层的问题没有再往下查（超出这张票的范围）；确认过和资产路径是否转义包根目录（`../` vs 包内的 `assets/...`）无关——换成包内路径问题依然存在。
2. **样例，在 `flutter test --platform chrome`（web）下**：测试体里直接调用 `rootBundle.loadString()`（不经过 provider）在 VM 上没问题，但在 `--platform chrome` 下，同一个测试文件里第二次调用同一份资产会在 30 秒后 `TimeoutException`。触发条件和第 1 种不完全一样（这里没有 provider、没有完整 App），但同样是“同一份自定义资产第二次读取”。

两种表现没有再往下查具体是 Flutter 测试框架的什么内部机制（`rootBundle`/`TestDefaultBinaryMessenger`/web 的资产服务，具体哪一层没有定论），只确认了规避方法：**不在测试或应用代码里对着这些契约文件调用 `rootBundle.loadString()`**，改成上面“App 怎么读”一节的内嵌常量方案；运行时/测试时不再有任何异步资产加载，两类问题都随之消失（`flutter test` 和 `flutter test --platform chrome` 都反复跑过同一批测试文件多次验证）。

后续子 SPEC 往 `schema/`、`samples/` 加文件时，照这个模式：加完文件跑一次 `tool/gen_ui_protocol_schemas.sh`，不要在 App 代码或测试里新增任何读取 `app/assets/contracts/ui_protocol/` 的 `rootBundle` 调用。

## 影响

- 新依赖：服务端 `jsonschema`；App `json_schema`。
- 新生成产物：`app/lib/ui_protocol/embedded_assets.g.dart`（`tool/gen_ui_protocol_schemas.sh` 生成，改了 Schema/样例后要重新跑并提交，类似 `tool/gen_api_client.sh` 的用法）。
- 后续子 SPEC 不新起一套契约目录，新增组件类型、大版本、样例都照 `app/assets/contracts/ui_protocol/` 现有的目录结构加文件。
