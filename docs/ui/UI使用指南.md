# UI 使用指南

规范本身（是什么、为什么）在 [`UI规范.md`](UI规范.md)。这份讲**怎么用**：写界面的人、画样稿的人、服务端组合页面的人各自该做什么。

> 下面提到的 `app/lib/ui_protocol/` 是 #18（SPEC-009.1，PR #85）的实现，合并到 main 之前只在分支 `claude/spec-009-1-ui-protocol` 上。文件名以合并后的 main 为准。

## 1. 写一个新界面前，先想清楚三件事

1. **它在固定骨架里，还是在服务端组合的内容里？**
   - 固定骨架（底部五入口：今天、发现、新建、记录、我的；主要按钮位置；做菜模式的操作方式；记录卡入口）由 App 自己写，不走协议。
   - 会随人、随场景变的内容（“今天”页里的提示、清单、建议）走协议：服务端下发页面描述，App 按描述渲染。
2. **每块内容有没有“结论、依据、明细”三层？** 至少要有结论；有系统替用户改过的地方，就必须有依据，并带来源标记。
3. **这块内容的每个动作是不是已登记的意图？** 不是就先登记意图，不要在组件里直接写跳转或调接口。

## 2. 用颜色、字体、间距

- 一律从主题取：`app/lib/app/theme.dart` 的 `GramTreePalette`（原始色值）和 `GramTreeColors.of(context)`（按当前明暗取色）。**组件里不写死颜色值**。
- 酱红只给“系统替你改了”（口味换算、场景调整）；主按钮用墨色；已验证用绿。别拿酱红做普通强调、警告或装饰。
- 标题用 Noto Serif SC，正文 Noto Sans SC，数字（用量、时间、计数）用 DM Mono。
- 卡片外观直接用 `ComponentCard`（`components/component_scaffold.dart`），不要每个组件自己画一遍：它已经处理好三档详略、读屏文案和卡片样式。
- 系统字号放大到 130%、160% 时不能截断或重叠，两档都要在界面测试里看一遍。

## 3. 新增一个组件（App 端）

登记一个组件只需要四样，在 `component_registry.dart` 的 `defaultComponentRegistry` 里加一条 `ComponentSpec`：

| 要给的东西 | 说明 |
|---|---|
| `type` | 类型名，小写下划线，如 `ingredient_list` |
| Schema 文件 | `contracts/ui_protocol/schema/<版本>/components/<type>.schema.json`，服务端和 App 共用；改完跑 `tool/gen_ui_protocol_schemas.sh`，把内嵌的 Dart 常量一起提交 |
| `builder` | 渲染函数：拿到组件描述、标准空态、动作回调，返回 widget；用 `ComponentCard` 搭三层 |
| `emptyState` | 标准空态文案（标题必填，一句说明可选）。结论层拿不到内容时显示它 |

写 `builder` 时：

- **简略**只放结论和一个主要动作；**标准**加依据入口；**详细**摊开依据，最下面放进明细页的入口。三档各显示什么由组件自己定，但档位由服务端定，组件不能自己改档位。
- 读屏标注：整个组件包一层 `Semantics`，读出结论、当前档位下显示的依据和动作文案。带来源标记的数值要读成“生抽 8.5 毫升，按你的口味换算过，点两下看原因”这种话。`ComponentCard` 已经按这个做好。
- 动作约定：`actions[0]` 是主要动作，`actions[1]`（如果有）是明细动作，只在详细档显示。
- 数据里有 `basis.text` 就是依据层文案；按钮文案不给时用意图的默认文案。
- 组件测试只看页面显示和操作结果（三档各渲染一次、空态、点动作后去了哪儿），不测内部 widget 结构。

## 4. 新增一个意图

意图登记表在 `intent_registry.dart` 的 `defaultIntentRegistry`。加一个 `IntentSpec`：名字、默认按钮文案、参数格式校验、处理器（暂时没有处理器的可以先留空，只登记名字和参数格式）。

- 按钮、菜单、以后的一句话输入都汇到这张表，走同一个处理器（`IntentDispatcher`）。**不要在组件里绕开它直接跳转或调接口。**
- `open_page` 只能打开 `registered_pages.dart` 里登记过的页面，任意网址一律拒绝。新页面要先在这里登记。
- 描述里出现没登记的意图或参数格式不对，整页会退回标准布局（原因码 `illegal_action`），所以服务端和 App 的登记表要同步加。

## 5. 来源标记和“为什么”面板

- 数值或文字被系统改过，就带上对应来源标记：`taste_adjusted`（口味）、`scene_adjusted`（场景）、`ai_estimated`（AI 估算）、`verified`（已验证）。作者原值（`author`）不带标记。
- 每个标记都要能点开同一个“为什么”面板，不要自己做第二种解释弹窗。面板里的依据写日期和档位，不写内部分数。
- 过敏提示、食品安全提醒是**必显内容**：面板只能看依据，不能给“这次不用”“以后别这样”。
- 两个反馈动作对应意图 `skip_this_time`、`dont_do_again`，并会记 `ui.source_feedback` 事件；打开面板本身也记一条事件。

## 6. 兜底与离线（服务端和 App 都要遵守）

- 服务端超过 800 ms 没回、协议大版本不认识、组件或动作没登记、数据格式不对、缺少必显组件、服务端报错——整页改用标准布局，用户看到的和默认组合一样。
- 离线时只有内容版本对得上才用缓存的描述，并写明是什么时候的。
- 每次兜底，原因码写进“组合展示”事件。
- 服务端不能下发脚本、任意网址或任意布局；App 请求时带上自己支持的协议版本和已登记的组件类型，服务端只下发 App 认识的。

## 7. 画新的界面样稿

有界面的子 SPEC，拆完票、写代码之前先画样稿（CLAUDE.md 第 1 节）：

1. 参照 `docs/ui/component-library.html` 的配色、字体、来源标记和三档详略来画；浅色和深色都要有。
2. 用 Artifact 发布，在开发线程里给出链接，不等确认直接开发，用户有意见再改。
3. **同时把样稿源文件存进 `docs/ui/`**（ASCII 文件名，如 `today.html`；多文件样稿放子目录，像 `recipe-detail/`），并在 `docs/ui/README.md` 的表里加一行，写上对应 SPEC 和 Artifact 链接。不能只留在 claude.ai。
4. 样稿里和 UI 规范不一致的地方，先改 `UI规范.md`，并在 PR 里说明，不要让样稿和规范各说各话。

## 8. 合并前的界面自查清单

- [ ] 颜色、字体全部从主题取，没有写死的色值
- [ ] 酱红只出现在“系统替你改了”的地方
- [ ] 内容有结论；有依据的地方带来源标记，点开是同一个“为什么”面板
- [ ] 三档详略都渲染过；空态有标准文案
- [ ] 读屏标注已加；130%、160% 字号不截断
- [ ] 每个动作都是已登记的意图，没有绕开意图直接跳转
- [ ] 浅色和深色都看过
- [ ] 网页版能编译（`flutter build web`），手机专有能力放在接口后面
- [ ] 新样稿已存进 `docs/ui/` 并更新了 README
