# UI 规范

出处：子 SPEC #18（SPEC-009.1 界面描述协议与组件库）和 #34（SPEC-009.2 按场景组合页面）、父 SPEC #9 的 Change Log、`component-library.html` 样稿。配色和字体的代码在 `app/lib/app/theme.dart`（`GramTreePalette`、`GramTreeColors`），组件从主题取，**不要写死颜色值**。

## 1. 原则

- **薄 UI、厚内核**：复杂逻辑放在服务端，界面只负责展示。
- 每个组件分**结论、依据、明细**三层。
- 一套统一的**来源标记**。
- 共用一个“**为什么**”面板。
- 按钮和一句话输入走**同一套意图**。

## 2. 配色

| 用途 | 浅色 | 深色 |
|---|---|---|
| 纸（页面底色） | `#F7F4EE` | `#171511` |
| 卡片 | `#FFFDF9` | `#221F1A` |
| 墨（正文、主按钮） | `#1B1813` | `#F1ECE3` |
| 酱红（强调色） | `#B0441E` | `#E07A52` |
| 已验证绿 | `#4E6B48` | `#8DAE84` |
| 次要文字 | `#5E574C` | `#B9B1A4` |

- 酱红**只用在“系统替你改了”的地方**（按口味换算、按场景调整），并把数值本身也染成酱红；主按钮用墨色，不用酱红。
- 已验证用绿。
- 不靠颜色区分：颜色之外还有图形和文字。
- 深色一栏是样稿提议的定稿值，由 #18（票 #80）落地。

## 3. 字体

| 用途 | 字体 |
|---|---|
| 标题 | Noto Serif SC |
| 正文 | Noto Sans SC |
| 数字 | DM Mono（等宽） |

支持系统字号 100% / 130% / 160%。字体文件打包由 #18 定稿。

## 4. 来源标记

五种来源，一套样式：

| 来源 | 协议取值 | 显示 |
|---|---|---|
| 作者填写 | `author` | 默认状态，不显示标记 |
| 按你的口味换算 | `taste_adjusted` | “口味”标记，酱红 |
| 按场景调整 | `scene_adjusted` | “场景”标记，酱红 |
| AI 估算 | `ai_estimated` | 虚线标记，表示还没人确认 |
| 已验证 | `verified` | 绿色标记 |

读屏标注示例：“生抽 8.5 毫升，按你的口味换算过，点两下看原因”。

## 5. 结论 · 依据 · 明细

同一个组件有三档详略，由服务端决定用哪一档，档位里显示什么由组件自己决定：

- **简略（brief）**：结论 + 一个主要动作。
- **标准（standard）**：多一个依据入口。
- **详细（detailed）**：把依据摊开，最下面是进明细页的入口。

## 6. “为什么”面板

- 点任何来源标记，打开的都是同一个面板：原值和现在的值、用大白话写的依据、来源引用、两个反馈动作。
- 依据只写日期和档位，不写内部分数。
- 两个反馈动作：
  - **这次不用**（意图 `skip_this_time`）：只影响这次查看，服务端重新算一遍不含这条调整的结果，口味档案不变。
  - **以后别这样**（意图 `dont_do_again`）：写一条来源反馈，由口味学习（SPEC-005.3）或场景规则（SPEC-009.2）决定怎么改。
- 必显内容（过敏提示、食品安全提醒）上的面板可以看依据，但没有这两个反馈动作。
- 打开面板本身也记一条事件：组合 ID、组件实例、来源类型。

## 7. 通用组件

#18 登记：`hint_bar`（提示条，普通 / 必显）、`section_title`、`text_block`、`list`、`empty_state`，另有 `source_mark`、`why_panel`。业务组件（食材清单、步骤卡、计时器等）以后按同一方式登记。

每个组件登记：类型名、数据格式（JSON Schema，两端共用，#18 落地后放在 `contracts/ui_protocol/`）、三档详略的渲染方式、标准空态文案、读屏标注。

## 8. 动作即意图

按钮和一句话输入最后都变成同一个登记过的意图，得到同样的预览和确认。一句话怎么理解是 SPEC-003 的事，这里只规定它们汇到哪。

本子 SPEC 登记的意图：`open_page`（只能是 App 登记过的页面）、`start_cooking`、`open_record_card`、`call_operation`（登记过的接口操作）、`save_to_taste`、`apply_change`（处理器由后续子 SPEC 补）、`skip_this_time`、`dont_do_again`。

服务端不能下发脚本、任意网址或任意布局。描述里出现没登记的意图，整页改用标准布局。

## 9. 兜底和离线

整页改用标准布局的情况（原因代码写进“组合展示”事件）：

| 情况 | 原因代码 |
|---|---|
| 协议大版本不认识 | `unknown_major` |
| 未登记的组件 | `unknown_component` |
| 未登记的动作 | `illegal_action` |
| 数据不符合格式 | `invalid_data` |
| 缺少必显组件 | `missing_required` |
| 服务端报错 | `server_error` |
| 等待超过时限（配置项，初始 800 ms） | `timeout` |

- 标准布局和默认组合看起来一样，用户不会察觉。
- 离线时只有内容版本对得上才用上次缓存的描述，并写明是什么时候的；对不上就用标准布局。
- 底部五个入口（今天、发现、新建、记录、我的）任何情况下都不变。

## 10. 页面描述协议 1.0

服务端按描述组合页面，App 渲染前再校验一次。App 请求时带上自己支持的协议版本和已登记的组件清单，服务端只下发 App 认识的组件。Schema 以 #77 定下、#18 落地的 `contracts/ui_protocol/` 为准（见 #18 的 PR 里的 `docs/adr/0005-界面描述协议共享契约.md`）；示例：“今天”空态页。

```json
{
  "protocol": "1.0",
  "page_type": "today",
  "composition_id": "7c9e6679-…-2d1a",
  "generated_at": "2026-09-28T10:30:00Z",
  "cache": { "depends_on": { "plan": "v0" }, "ttl_s": 600 },
  "experiment": null,
  "components": [
    { "type": "hint_bar", "id": "c1", "detail": "brief",
      "data": { "conclusion": "先添加一道你常做的菜" },
      "actions": [{ "intent": "open_page", "params": { "page": "create" } }],
      "reason": { "code": "default", "text": "默认组合" },
      "required": false },
    { "type": "empty_state", "id": "c2", "detail": "standard",
      "data": { "conclusion": "今天还没有安排",
                "basis": { "text": "这里会显示今天要做的菜" } },
      "actions": [{ "intent": "open_page", "params": { "page": "create" } }],
      "reason": { "code": "default", "text": "默认组合" },
      "required": false }
  ]
}
```

固定骨架不在描述里：底部五入口、主要按钮的位置、做菜模式的操作方式、记录卡入口。
