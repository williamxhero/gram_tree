一个组件的三档详略

同一个组件在三档详略下的样子。简略只给结论和一个主要动作；标准多一个依据入口；详细把依据摊开，最下面是进明细页的入口。服务端决定用哪一档，档位里显示什么由组件自己决定。

通用面板

“为什么”面板

点左边手机里任何一个来源标记，打开的都是同一个面板：原值和现在的值、用大白话写的依据、来源引用，底下两个反馈动作。依据只写日期和档位，不写内部分数。

可以点。点“口味”“场景”“AI 估算”“已验证”标记都会打开面板；试试“这次不用”。

必显内容上的面板没有反馈动作。过敏提示、食品安全提醒可以看依据，但不能选“这次不用”或“以后别这样”。

两个反馈动作

  • 这次不用：只影响这次查看。服务端重新算一遍不含这条调整的结果，口味档案不变。意图 skip_this_time。
  • 以后别这样：写一条来源反馈，由口味学习（SPEC-005.3）或场景规则（SPEC-009.2）决定怎么改。意图 dont_do_again。
  • 打开面板本身也记一条事件：组合 ID、组件实例、来源类型。
通用组件

提示条、分区标题、文字块、列表容器、标准空态

这五个组件由 #18 登记，业务组件（食材清单、步骤卡、计时器等）以后按同一方式登记。每个组件都有标准空态和读屏标注。

从上到下：提示条（普通 / 必显）、分区标题、文字块、列表容器。

标准空态，也是“今天”入口第一张用协议的页面：提示条 + 标准空态，服务端默认组合下发。

每个组件登记的内容

  • 类型名，如 hint_bar、section_title、text_block、list、empty_state、source_mark、why_panel
  • 数据格式（JSON Schema，两端共用）
  • 三档详略的渲染方式
  • 标准空态文案
  • 读屏标注，例如来源标记读作“生抽 8.5 毫升，按你的口味换算过，点两下看原因”
动作即意图

按一下，或者说一句，走的是同一个意图

按钮和一句话输入最后都变成同一个登记过的意图，得到同样的预览和确认。一句话怎么理解是 SPEC-003 的事，这里只规定它们汇到哪。

可以点。点“少放点咸”，或在输入框里写一句再按“发送”，出来的都是下面这张预览卡。

意图登记表（本子 SPEC）

  • open_page 打开页面，只能是 App 登记过的页面
  • start_cooking 开始做
  • open_record_card 打开记录卡
  • call_operation 调用登记过的接口操作
  • save_to_taste、apply_change 存进口味、应用改动（处理器由后续子 SPEC 补）
  • skip_this_time、dont_do_again 这次不用、以后别这样

服务端不能下发脚本、任意网址或任意布局。描述里出现没登记的意图，整页改用标准布局。

兜底和离线

出问题时用户看到什么

标准布局和默认组合看起来一样，用户不会察觉。离线时只有内容版本对得上才用上次的描述，并写明是什么时候的。底部五个入口在任何情况下都不变。

fallback: true reason: timeout # 超过 800 ms composition_id: — # 标准布局没有组合
source: local_cache content_version: 一致 → 用缓存 不一致 → 标准布局

整页改用标准布局的情况

  • 协议大版本不认识 unknown_major
  • 未登记的组件或动作 unknown_component / illegal_action
  • 数据不符合格式 invalid_data
  • 缺少必显组件 missing_required
  • 服务端报错 server_error
  • 等待超过时限 timeout（配置项，初始 800 ms）

原因代码写进“组合展示”事件，用来发现服务端问题。

固定骨架不在描述里

  • 底部五入口：今天、发现、新建、记录、我的
  • 主要按钮的位置
  • 做菜模式的操作方式
  • 记录卡入口

App 请求时带上自己支持的协议版本和已登记的组件清单，服务端只下发 App 认识的组件。
